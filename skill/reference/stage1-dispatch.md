### 3. STAGE 1 — DISPATCH IN DEPENDENCY WAVES, NOT ONE FLAT PARALLEL BATCH

**Rewritten 2026-09-06 after auditing whether findings actually flow between sub-agents. They did not.** Everything used to go out in one parallel batch, so no agent could see any other's findings — fine for agents that observe independent things, fatal for agents whose whole job is to INTERPRET what the others found. Four failures, all in the single 2026-09-06 deep run, none detected by anything:

1. **EVIDENCE GAP.** `smith-thesis` wrote APH `strengthening` with `evidence_against: "none found this run"`. `smith-quality`, the same run, found APH interest expense **+157% QoQ**, debt +21%, goodwill +66%. The G58 rule that both sides must survive compression is simply defeated by parallelism — the counter-evidence existed in a sibling's output the agent could not read.
2. **HANDOFF TO NOWHERE.** `smith-thesis` closed a tension with *"proximate cause unresolved, handed to smith-catalyst"*. Catalyst had already run, in parallel. Thesis's verdict was formed without the answer catalyst had in fact found.
3. **UNADJUDICATED CONTRADICTION.** `smith-catalyst` reported a STRUCTURAL memory tailwind (DRAM +50%/NAND +60% QoQ); `smith-cycle` reported TrendForce 4Q26 at **+3–8%**. Directly opposed, neither saw the other, both went into the briefing. The catalyst figure later failed tier-1 corroboration outright.
4. **READ-WRITE RACE.** An agent read `lots.json` while it was being rebuilt (2026-09-06) and reported mismatches that did not exist. Anything that writes lots or trades runs in Wave 0, before any reader.

**THE WAVES.** Dispatch in this order. Within a wave, agents are genuinely independent and go in parallel.

**WAVE 0 — FACTS. Script-first; nothing that reads these files may run until it finishes.**
The ledger pipeline (`ledger-parse` → `ledger-apply --write` → `lots --write`), then `bookcalc` and `taxcalc`. This is what closes failure 4: `lots.json` reaches its final state before any agent opens it. On the normal path no agent is dispatched here at all.

**WAVE 1 — OBSERVERS. Parallel. They read the outside world and each other's absence costs nothing.**
`smith-catalyst` · `smith-signals` · `smith-watchlist` · `smith-scout` · `smith-earnings` · `smith-quality` · `smith-rebound` (moved from Wave 2 on 2026-09-15: every input it reads is a Wave-0 compute file, so waiting on Wave 1 only added latency)
These answer *what happened* — news, prints, filings, sessions, positioning. None of them needs another's verdict.

**`smith-scout` absorbed smith-macro (retired 2026-09-14) and is a Wave 1 member.** On a quick run the MACRO trigger dispatches it in `macro_only` mode alongside Wave 1. Its tail reaches the strategist through `scout_tail` in `AGENT_SLICES["strategist"]`, so merge it with Wave 1 (`merge-tails --agents scout`) before the §4 strategist slice renders.

**THEN, before dispatching Wave 2: merge Wave 1's tails (`merge-tails --agents <wave 1 list>`, per its own per-wave instruction above), then re-render Wave 2's slices** (`python3 scripts/smith_math.py slices --base-dir . --run-dir runs/<ts> --mode deep --today <date> --agents thesis,cycle`). This second `slices` call is what makes the Wave-2 embeds below real: `AGENT_SLICES["thesis"]`/`["cycle"]` reference Wave-1 agents' own `out_<agent>.json` files as refs (added 2026-09-07, closing a gap where this whole promise was prose-only — the WAVES design existed in this document for weeks before `AGENT_SLICES` was ever updated to actually deliver it), and those files don't exist until Wave 1 has landed. Skipping this second `slices` call silently degrades Wave 2's embeds back to state-only, the exact failure this rewrite exists to prevent.

**WAVE 2 — INTERPRETERS. Parallel with each other, but only after Wave 1 has merged AND slices have been re-rendered.**
`smith-thesis` · `smith-cycle` · **`smith-cluster` × up to 3 (see CLUSTER trigger in §3b)**
Each receives the Wave-1 tails it depends on, via its own re-rendered slice (`read_these_files`, not hand-pasted):
- **thesis** ← catalyst's events, quality's flags, signals' buckets (`AGENT_SLICES["thesis"].refs`: `catalyst_tail`, `quality_tail`, `signals_tail`). It cannot write an empty `evidence_against` on a name a sibling flagged.
- **cycle** ← catalyst's events (`refs`: `catalyst_tail`). The memory contradiction becomes an input to adjudicate, not a briefing footnote.
- **cluster** ← its own cluster's row from `compute_ladder.json` (Wave 0), plus catalyst's events, signals' buckets, quality's flags and earnings' facts (`refs`: `ladder`, `catalyst_tail`, `signals_tail`, `quality_tail`, `earnings_tail`). All four tails are OPTIONAL by design — quality is monthly, earnings fires only near a print — so a MISSING one is expected and is not reported as a problem.

  **Add the dispatched cluster keys to the re-slice call**, e.g. `--agents thesis,cycle,cluster_semis,cluster_optics,cluster_memory`. The keys come from `compute_ladder.json`'s `dispatch_selected`; do not invent them. Each renders its own `slice_cluster_<slug>.json` naming the cluster in `cluster_name`, and each returns to its own `out_cluster_<slug>.json`. **All of them run the single `smith-cluster` agent definition** — there is no `smith-cluster_semis.md` and there never will be; the per-cluster knowledge is `policy.cluster_playbooks`, which is data.

**THEN: `python3 scripts/smith_math.py crosscheck --base-dir . --run-dir runs/<ts> --today <date>`** — moved here, AFTER Wave 2, 2026-09-07 (corrected from an earlier version of this section that ran it before Wave 2; see `cmd_crosscheck`'s own docstring for why that timing left 4 of its 5 rules structurally inert — `evidence_gap`, `thesis_vs_catalyst_threat`, `catalyst_vs_cycle`, and `thesis_vs_price` all read `thesis`'s or `cycle`'s ACTUAL WRITTEN OUTPUT, which doesn't exist before Wave 2 runs; only `handoff_to_nowhere` could ever fire at the old invocation point). It can no longer *prevent* a bad verdict — that job belongs to the Wave-2 embed above, which puts the evidence in front of thesis/cycle before they write anything. What it catches now is the backstop case: an interpreter had the evidence and still produced a conflicting verdict, or an unresolved tension between two interpreters. Writes `crosscheck.json` to the run dir; `AGENT_SLICES["strategist"]` already refs it, so **every `high` finding reaches Wave 3 through the normal slice mechanism, not hand-pasting.**

**WAVE 3 — `smith-strategist`**, consuming a set of verdicts that have actually seen each other, plus any tension crosscheck found between them.

**What this costs.** Wave 2 now carries up to three `smith-cluster` dispatches on a deep run (gated and round-robin'd by `cmd_ladder`, never on quick) — that IS an extra cost, roughly 75-145K tokens each, and the gate exists precisely because dispatching all seven held clusters every deep run would roughly double fleet cost for rankings that move on quarters. Everything else below is unchanged: no extra dispatches. Wave-2 prompts carry Wave-1 tails, which is a modest embed increase and is likely net NEGATIVE on tokens — thesis no longer searches for what catalyst already found. The real cost is **latency**: five serial stages instead of two (Wave 0, Wave 1, re-slice, Wave 2, crosscheck, Wave 3 — six, really, once the re-slice step is counted honestly). A deep review takes longer in wall-clock. That is the correct trade — the alternative is verdicts formed without available evidence, which is what produced all four original failures this rewrite fixed.

**The old flat-parallel roster is preserved below for the trigger conditions and per-agent embeds; the WAVES above govern ORDER.**

### 3b. Roster, triggers and embeds
- **QUICK roster (trimmed 2026-09-14 — was 3 unconditional agents, now 1; the user's own read: "the quick sweep has become too extensive and heavy").** `smith-signals` is the only agent dispatched on every quick sweep. It is the direct source of triggers/proposals and the mechanism that decides whether either of the two below needs to run — cutting it would gut quick mode's purpose. `smith-thesis` and `smith-watchlist` are now CONDITIONAL on quick (see their own trigger entries below); book and scout remain script-covered in quick mode, not dispatched.
- **DEEP roster**: `smith-signals`, `smith-thesis`, `smith-watchlist`, `smith-scout` (mode `full`: session, sentiment, Fed/options/calendar/regime, diversifier bench) and `smith-catalyst`. All mandatory on every deep run — do not drop any silently. `smith-scout` ALSO dispatches on a QUICK run in `macro_only` mode when the MACRO trigger fires. (smith-book, smith-macro and smith-tax were retired 2026-09-14: betas and the book narrative inputs come from `indicators`/`bookcalc`, macro folded into smith-scout, lot sequencing is `taxcalc` plus one strategist sentence.)
- **THESIS trigger (added 2026-09-14, replaces unconditional quick dispatch).** Dispatch `smith-thesis` on a QUICK run when ANY of: (a) `compute_triggers.json` fired a LIVE trigger this run on a held ticker (`oversold_reversion`, `overbought_distribution`, `catalyst_threat`, `stretch`) — per §2.9d's own principle, "price says WHEN, thesis says WHICH WAY," so a live price trigger without a fresh thesis read is half an answer; (b) `freshness --base-dir .` reports the `thesis` artefact `stale` or `dark` (past its 21-day TTL) for any held name; (c) `validate`'s EARNINGS VERIFY surfaced a stuck-PENDING entry for a held name (a post-print status change needs adjudication); (d) the user explicitly asks about a specific holding's story. **If none fire, skip the dispatch** and state it plainly in §5's THESIS CHECK section — "Thesis: unchanged since `<as_of>`, no live trigger or staleness this run" — reading `state.thesis` as-is. This does not weaken `catalyst_threat`/`thesis_break` trigger generation: both are script-computed from whatever `state.thesis` currently holds (`smith_risk.thesis_status`), not from a fresh dispatch each run — skipping thesis just means the cached status persists one more run before its next real check, exactly the behavior already implied by its own 21-day TTL. DEEP runs are unaffected — thesis stays mandatory there.
- **WATCHLIST trigger (added 2026-09-14, replaces unconditional quick dispatch).** Dispatch `smith-watchlist` on a QUICK run only when the user explicitly asks ("check my watchlist," "any entry setups," "what's on my watchlist") — otherwise not dispatched. Rationale: it scans for NEW candidates you don't currently hold, and even on deep runs covers only a rotating slice of the list per run (`watchlist_scan_cursor`) — missing a signal on a name you don't own is lower-stakes than missing one on a held position, and it was the least differentiated of the three original mandatory agents. State "Watchlist: not scanned this run (quick mode, no explicit ask)" in §5's WATCHLIST section when skipped. DEEP runs are unaffected — watchlist stays mandatory there.
- **REBOUND trigger — REWRITTEN 2026-08-30 on the user's own restatement of the mandate; widened 2026-09-15.** Dispatch `smith-rebound` in parallel with Stage 1 on **any** sweep whenever `compute_triggers.json`'s `correction_state` is `pullback`, `correction` or `deep_correction`. That field is computed deterministically from the book's live drawdown against `policy.drawdown_warn_pct`, the benchmark's 1-month return, and breadth of held names down 10%+ — three independent routes, any one of which qualifies. **`pullback` was excluded until 2026-09-15**, on the theory that the mildest tier didn't warrant the dispatch — but the user pointed out this screen exists *for* pullbacks specifically, and the gate as written meant it never refreshed while the book sat in pullback territory (measured: `rebound_candidates` went dark for 15 straight days across several pullback-tier sweeps, because none of them ever crossed into full `correction`). All three non-`none` tiers now qualify.

  **What this agent is actually for**: finding names that have fallen too far in a BROAD CORRECTION, biased toward HIGH-VOLATILITY names, as candidates to buy for a relief rally. High volatility is the *thesis* here — it is what makes the bounce worth catching — not a risk to screen out.

  **Three things it must NOT be gated on, because each of them wrongly suppressed it before:**
  1. **Stop-outs.** It does not need the user to have been stopped out. Its old file framed it as a "Rapid Redeployment Desk" whose first rule was stop-loss forensics, so runs with no stop-outs skipped it as having no job.
  2. **Spare cash.** A rebound candidate list is equally the BUY leg of a rotation. This book runs ~3% cash by design; gating on deployable cash retires the agent permanently. The 2026-08-26 run skipped it explicitly for "$124.52 of cash".
  3. **The pre-market futures gate.** `gate_classification` answers "is this morning scary", which is a different and much noisier question than "has this book actually corrected". The 2026-08-29 run skipped it because the gate read ESCALATING off a stale Friday close on a closed Saturday. `correction_state` is the right question; the gate stays useful as *timing* context inside the agent, not as its dispatch condition.

  **SIZING (added 2026-08-30, policy amendment).** A rebound entry is sized off its ACTUAL stop — just under the support level the agent supplies — not off 2×ATR below spot. Same 0.5%-of-book risk budget, shorter stop, larger position: risk is not increased, it is measured where it sits. When passing its proposals to `add-proposal`, carry `trigger_type: "rebound"`, `support_usd` and `price_at_proposal`; the command applies `smith_risk.support_anchored_cap` itself. The stop is floored at `0.5 × atr20_pct` and 3%, which both prevents the whipsaw the 2×ATR rule exists to stop and bounds the uplift to 4×. No support level means no exception — sized by the standard rule and stamped with the reason. **The aggregate open-risk cap still binds and is currently breached, so the sizing path stamps a `FUNDING REQUIRED` review flag naming how much risk must be freed; treat these as the buy leg of a rotation, not a standalone add.**

  Embed: `compute_triggers.json`'s `rebound` block (the deterministic candidate pool, already screened for fall depth, volatility floor and the falling-knife thesis gate), holdings.json, state.json and policy.json slices, plus this run's `gate_classification` as timing context. **Its returned `proposals` array MUST be persisted at §7** — `merge-tails` now covers it (`state.rebound_candidates`). Before 2026-08-30 it had no merge rule and no state key at all, so every candidate list it ever produced was discarded; the 2026-08-24 run named four rebuy candidates and none survived the run. That is the G50 shape, and it is part of why the agent looked unused: it was not only being skipped, it was being forgotten on the runs it did work.
- **CLUSTER trigger (added 2026-09-08; full mechanics moved to `reference/deep-mode-dispatch.md` 2026-09-14 — this was 11 lines of pure duplication against that file's own "CLUSTER SPECIALISTS" section, read on every quick sweep for a trigger that can never fire on one).** Dispatch `smith-cluster` as a WAVE 2 member, once per cluster, for the clusters named in `compute_ladder.json`'s `dispatch_selected` — **DEEP runs and explicit on-demand requests only, never on a quick sweep.** Load `reference/deep-mode-dispatch.md`'s CLUSTER SPECIALISTS section before dispatching for the trigger gate, embed contents, merge rule and failure modes.

- **CATALYST trigger** (full incident on why this exists at all: DECISIONS.md#G30): dispatch `smith-catalyst` as a WAVE 1 member (see §3's WAVES, 2026-09-06) when ANY of: gate = ESCALATING · SMH moved ≥3% in either direction · any Asia index moved ≥3% overnight · any cluster moved ≥4% · this is a DEEP run · the user asks why something moved. It is a WebSearch-only agent with a fixed ≤6-query budget, targeting under 90 seconds, so the cost of dispatching it on a false alarm is small next to the cost of missing a real one. Embed: `factor_themes` from state.json, trimmed holdings rows, `cluster_table`, news_watermark, its own prior tail, market_session, the trigger reason, and **`state.catalyst_suppressed`** (the dashboard's "already priced in" button list; tell the agent not to re-surface a suppressed (headline, date) pair). Its returned `catalysts` and `theme_updates` MUST be written back at PERSIST (§7, see the factor_catalysts bullet there) — dispatching this agent and discarding its output is the G50 shape.
- **MACRO trigger (added 2026-09-14).** On a QUICK run, dispatch `smith-scout` in `macro_only` mode whenever `market_inputs.json` shows **`|us10y_change_pts| ≥ 0.12` (12bps)** OR **`vix ≥ 22.0`** — a fast yield spike or a vol-regime flip is the macro shock this single-factor book is most exposed to. It runs alongside Wave 1; merge it with Wave 1 before the strategist slice renders.

  It fetches nothing for options: `compute_options.json` is script-computed on deep runs, and absent on quick runs (the options fields are then `null`).

  Merge: `merge-tails --agents scout` writes the macro fields into `macro_read` and `fomc_cache`, and leaves the diversifier bench untouched when a `macro_only` tail omits it. §5's MACRO REGIME section keys off "smith-scout ran", not off the run mode.

- **LEDGER — SCRIPT-FIRST, AGENT ONLY ON EXCEPTIONS (rewritten 2026-09-06).** Whenever `build-holdings`' `qty_changes` is non-empty, on EVERY sweep type including quick and refresher, run this pipeline yourself — BEFORE `pipeline` (§2 step 3.5). Do NOT dispatch `smith-ledger` first.

  1. `search_threads` — `from:transactions.indmoney.com subject:(BUY OR SELL) after:<prev run date>`, pageSize 50, paginate on `nextPageToken`. Save every page verbatim to `runs/<ts>/ledger_threads.json` (a JSON list of the page objects).
  2. `python3 scripts/smith_math.py ledger-parse --base-dir . --threads-file runs/<ts>/ledger_threads.json --today <date>`
  3. **Only if `needs_body` is non-empty**, `get_thread` (PLAIN_TEXT) those specific thread ids — usually one — save the tool's returned JSON **verbatim** to `runs/<ts>/ledger_bodies.json`, and re-run step 2 with `--bodies-file`. **Never retype or reformat the body text into a hand-written wrapper** (found live 2026-09-10: a body was hand-retyped into a heredoc, the retyping lost the confirmation template's exact pipe-table spacing `ledger-parse`'s regex depends on, and the row never parsed — the same GOOG confirmation still unresolved as a result). Write the tool result's own JSON structure to the file exactly as returned; if you need to inspect it first, read it, don't reconstruct it.
  4. `ledger-apply --parsed-file <parse output> --write`. `pipeline`'s `lots` stage then rebuilds lots.json from the updated trades.json; on a refresher (no `pipeline`), run `lots --base-dir . --holdings runs/<ts>/holdings.json --write` yourself.
  5. **Dispatch `smith-ledger` ONLY if `dispatch_agent` is true** (an unresolvable ticker or a row whose numbers do not reconcile), or if `lots` reports a mismatch or `phantom_short`. Embed the parse output and the specific failing rows — never the whole mailbox.

  **Why this replaced a full agent dispatch.** smith-ledger cost **107,874 tokens and 24 tool calls** on 2026-09-06 to record SEVEN fills — second-largest agent in the fleet, largest in tool use — and essentially none of it was judgment. Worse, its own file carried a rule that was empirically false: it claimed the search snippet "truncates before `Shares:`/`Order Type:` on close to every one of these confirmations" and therefore instructed a `get_thread` for EVERY row. Measured against those same seven: **six of seven carried `Shares:` in the snippet, and both stop-sells carried `Order Type: stop`.** The snippet is a fixed-length field, so survival depends on how long the company NAME is — "Advanced Micro Devices Inc." was the one that overflowed. One body fetch was needed, not seven. Three tool calls would have done the whole job.

  **Why a regex may be trusted with money here.** Every parsed row must reconcile `Amount == Shares × Price` within the measured broker fee (**0.30% buy, 0.00% sell**, verified to three decimals across all seven). A row is accepted because three independently extracted numbers agree, not because a pattern matched; anything else is reported as a parse failure and never appended. TICKER INTEGRITY is preserved and fails closed: resolution is by exact name, then a **confirmed alias** in `data_cache.ticker_map_email_aliases`, then a **unique** prefix — and a bare "Alphabet Inc." matches BOTH share classes, so it resolves to nothing and goes to `unresolved_ticker` rather than silently becoming GOOG or GOOGL. Promote every `alias_suggestion` into the alias cache once verified, so resolution becomes a stored fact rather than a match.

  `ledger-apply` is idempotent on `message_id` with a `(date, ticker, qty, price)` fallback, so an overlapping date window or a re-run after a partial failure cannot double-count a fill — and a duplicated SELL is exactly the shape that silently corrupts FIFO.

Every agent's TOOLS section requires batching multi-symbol fetches (never loop single-symbol calls) and forbids reading state.json/ledger.csv wholesale — only their own prior output file, and only if the embedded tail is insufficient.

Each analyst writes its full output to output_file (capped: ≤120 lines for signals, ≤100 for others), returns a ≤8-line prose summary PLUS its fenced JSON tail verbatim + the path. signals and thesis return DELTA-only tails (`{"changed":{...},"unchanged_count":N}`) when most of the book is unchanged — you already hold the full prior map in state.json and merge the delta into it. Wait for all dispatched.

JSON TAIL DISCIPLINE (every agent, every dispatch): the fenced JSON tail is the last thing in the response — no text of any kind follows its closing fence. This is a parsing-reliability rule, not a style preference.

**merge-tails STAGES (2026-09-14):** it writes `runs/<ts>/state.pending.json`; later waves, `slices`, `crosscheck` and `report` read through it, and nothing reaches state.json until `commit-state` (§4). A run that dies mid-Stage-1 leaves state.json untouched and `health` reports the orphaned patch. MERGE THE TAILS MECHANICALLY, DON'T HAND-ASSEMBLE, AND MERGE **PER WAVE** (corrected 2026-09-07 — this line previously said merge once "once all of a run's agents have landed", which was a real bug once WAVES replaced flat-parallel dispatch): the moment each agent's notification arrives, WRITE its exact returned fenced tail to `runs/<ts>/out_<agent>.json` (a plain Write call — an agent's own self-written output_file can drift from what it actually returned). **Call `merge-tails` once per wave, immediately after that wave's agents land — never batch Wave 1 and Wave 2 into one call.** `python3 scripts/smith_math.py merge-tails --base-dir . --run-dir runs/<ts> --today <date> --agents <this wave's agents>`. Why this matters, not just tidiness: `smith-earnings` (WAVE 1) and `smith-thesis` (WAVE 2) can both write `state.data_cache.earnings_facts` for the same ticker in the same run, and the merge is a per-ticker overwrite with no conflict detection — whichever agent's write applies LAST wins. A single end-of-run call processes agents in `MERGE_RULES`' fixed dict order (`thesis` before `earnings`), which silently let Wave-1 earnings' OLDER fact overwrite Wave-2 thesis' NEWER, sibling-informed one — backwards from intent. Calling `merge-tails` once per wave, in wave order, makes the later wave's write land later by construction, so thesis correctly wins. Covers thesis/sector_map/earnings_facts, signal_history (+ stamping `signal_history_as_of`), factor_catalysts (REPLACE, never append) + factor_themes, betas, analyst_targets, atr20/rsi14/rel_strength_1m/ret_5d, quality_financials, diversifier_candidates, watchlist_scan_cursor, cycle, tax, rebound (`state.rebound_candidates`), strategist (`state.stress_table`, `stress_table_prev`), and fomc_cache. **The strategist's merge needs its OWN, THIRD call** — `--agents strategist` — right after Stage 2 returns; nothing else triggers it, and skipping this step is the exact G50-shape loss `_merge_strategist` was built to close (found live 2026-09-07: it was being skipped, because this line only ever described a single Stage-1 merge and never mentioned a post-Stage-2 one). `merge-tails` stamps `<key>_as_of` for everything it merges (`MERGE_STAMPS`, `freshness`'s data source) and gives each thesis entry a `reviewed_on`. **The one agent genuinely not covered by `merge-tails` is `ledger`** — it writes `trades.json`/`lots.json` directly via its own dedicated commands (`ledger-apply`, `lots --write`), by design, not as a gap.

`merge-tails` also advances `state.news_watermark` to today whenever a news-reading agent (signals/thesis/watchlist/catalyst) is in the merged batch (added 2026-09-07, mechanical fix — this key was dead code before: four agents were handed it every run and told to dedupe against it, but nothing ever wrote it back, so the dedup was permanently inert against a stale value). Nothing for the orchestrator to do here beyond calling merge-tails as already instructed.

**LOG USAGE ONCE, FOR THE WHOLE RUN — ONE BATCHED CALL, NOT A PER-AGENT LOOP (rewritten 2026-09-06).**

Every completion notification carries a `usage` block (`subagent_tokens`, `tool_uses`, `duration_ms`). Collect them as each agent lands, and when the run's agents are all in, make ONE call:

`python3 scripts/smith_math.py usage-report --base-dir . --run-id <ts> --mode <mode> --usage-file runs/<ts>/usage.json --today <date>`

where `usage.json` is a JSON list of `{"agent","tokens","tool_calls","duration_s"}`, one entry per dispatched agent **including the strategist**. It logs every row AND audits every row (trailing-median outlier vs the agent's own last 10 runs, plus any `AGENT_BUDGETS` breach), auto-writing a `correction` lesson for anything flagged, and returns the run total, mean, and largest/smallest agent.

**Why it is one call and why it raises.** This was a per-agent shell loop until 2026-09-06, when it broke: the loop split `agent:tokens:calls:secs` records with `set -- $a`, which does **not** word-split in zsh (unlike bash), so every argument arrived empty. `usage-audit` failed visibly because its output was read; `usage-log`'s was piped to `/dev/null` and it failed **silently for four of twelve agents**. The gap surfaced only when a cost question forced a read of `learning.json` and the table came back a third short — the instrumentation built to answer "what did this run cost" was itself missing a third of the run. So: one read-modify-write instead of twelve independent chances to fail, and a malformed row **raises** rather than being skipped, because a confidently partial cost figure is worse than no figure. Never redirect a state-writing command to `/dev/null` in a loop; if it is worth running it is worth checking it returned.

Put the run total in the briefing's data_quality when it is notable, and cite any flagged agent by pointing at the auto-logged lesson rather than re-explaining it in prose. **Read the total as an agent COUNT question first** — measured 2026-09-06, per-agent cost is nearly flat (75K–145K, a 1.9x spread against a ~75K floor), so the number of agents dispatched is the cost, not what any one of them did.
