# Priced refresh

> Moved verbatim out of SKILL.md on 2026-09-14 (core cut to <=60KB). Load this file only when the core step that cites it runs. Where this text and the core disagree, the core wins — it reflects the scripted flow (`preflight`, `smith_fetch.py`, `dispatch-plan`, `postflight`).

**Script changes since this text was written:** open a fresh run dir `runs/<run_id>-priced/` via `preflight` (never reuse the earlier run's dir — reuse made the materiality diff compare a file with itself); prices come from `smith_fetch.py all --sections macro,quotes`; step 3.5's materiality gate is `python3 scripts/smith_math.py triggers-diff --base-dir . --run-dir runs/<run_id>-priced`; persist with `postflight --phase commit --mode priced` then `--phase close`.

### 0.6. PRICED REFRESH (quick mode, added 2026-09-09 — closes the "proposals still pre-open" gap)

**Why this exists.** A plain REFRESHER (§0.5) only touches `book`/`attribution` — value, weights, P&L delta. Everything downstream of price — `market_session`, `gate_classification`, `compute_triggers.json`, and every open proposal's sizing/trigger — is left exactly as it was at the last full sweep, because triggers and proposals are keyed off price levels the refresher never recomputes. On 2026-09-09 this produced a dashboard that quoted live intraday prices under a header still labeled "pre-open," with all 12 open proposals sized against that morning's numbers hours after the market had moved. **The fix is not "run more agents" — triggers and proposals are `smith_math.py` output, driven by the compute pipeline, not by an LLM sub-agent.** Rerunning the deterministic pipeline on fresh prices and redispatching only the one agent that consumes it (the strategist) gets proposals current for roughly the cost of ONE extra agent call, not the 3-9 a full quick/deep roster costs.

**Trigger:** the user asks for updated/live/fresh PROPOSALS specifically (not just prices) — "refresh and give me updated proposals," "are the proposals still based on old prices," "priced refresh," "redo the proposals with live prices" — whether or not a §0.5 refresher already ran today. If a plain refresher hasn't run yet this call, step 1 below folds it in; if one just ran, reuse its `holdings.json`/`compute_book.json` rather than re-fetching.

**Steps, in order:**

1. **Live prices.** If not already done this call, run §0.5's ONE `networth_holdings(US_STOCK)` pull and build the refreshed `holdings.json` (reuse the existing run dir's file if a refresher just produced one — don't re-fetch).
2. **Recompute session/gate, not just prices — this is the part §0.5 skips and the part that broke on 2026-09-09.** Re-run the §1.5 market-inputs batch (check the cross-skill cache first, as always) and recompute `market_session` from current time vs US market hours + the holiday calendar, and `gate_classification` (GATE v2) from the fresh macro strip. Write both into `holdings.json`, replacing whatever the reused run dir had — a stale `pre-open` label under live intraday prices is exactly the contradiction this mode exists to close.
3. **Full compute pipeline, script-only, no LLM cost:** `python3 scripts/smith_math.py pipeline --base-dir . --run-dir runs/<ts> --today <date> --lots lots.json`. This regenerates `compute_risk.json`, `compute_drift.json`, `compute_rotation.json`, `compute_triggers.json`, `compute_derisk.json`, `compute_sentiment.json` etc. off the live prices from step 1-2 — triggers (`oversold_reversion`, `catalyst_threat`, `stretch`, all of §2.9d) now fire against where the book actually sits right now, not where it sat at the last full sweep.

3.5. **MATERIALITY GATE — do not dispatch the strategist on an unchanged trigger set (added 2026-09-14).** A `smith-strategist` dispatch costs ~75-145K tokens regardless of what it's asked to re-decide (measured fleet-wide, §3's own usage-audit finding) — that floor is paid whether triggers moved or not, so paying it on a no-op priced-refresh is pure waste. Before step 4, diff the fresh `compute_triggers.json` against the run dir named in `state.json.last_run_dir`'s own `compute_triggers.json` (or the prior priced-refresh's, whichever is more recent) on exactly three things: (a) the set of `(ticker, trigger_type)` pairs across `oversold_reversion`/`overbought_distribution`/`catalyst_threat`/`thesis_break`/`stretch`, (b) `compute_book.json`'s `cash_pct` crossing into or out of the policy band (a funding-status flip changes every proposal's fundability even with an unchanged trigger set), (c) `gate_classification` changing category (STABILIZING/AMBIGUOUS/ESCALATING). **If all three are unchanged, skip steps 4-7 entirely** — no `score`, no re-sliced strategist embed, no dispatch. Update state.json/holdings/session/gate, rebuild and republish the dashboard with the fresh prices, append the ledger row, and say so plainly: "Triggers unchanged since `<prior ts>` — prices refreshed, proposals carried forward untouched, strategist not redispatched." If ANY of the three moved, proceed to step 4 as normal — a changed trigger set is exactly what this mode exists to catch.
4. **`score`** (probe with `{}` first per its own interface, then fetch the named tickers + SMH) so the strategist consumes a live scorecard, same as any other dispatch — never skip this before Stage 2 per §4's existing rule.
5. **Re-render only the strategist's slice:** `python3 scripts/smith_math.py slices --base-dir . --run-dir runs/<ts> --mode quick --today <date> --agents strategist`. This is what hands the strategist the fresh `compute_triggers.json`/`compute_drift.json`/`compute_risk.json` via `read_these_files`, exactly as a normal Stage 2 dispatch does.
6. **Dispatch ONLY `smith-strategist`** — no Stage-1 roster. Embed `slice_strategist.json` as usual, PLUS the prior full sweep's Stage-1 tails (thesis/signals/watchlist output_file paths or inline tails from the last `runs/<ts>/`, whichever that run's briefing used), each labeled with its actual `as_of` date so the strategist can state plainly which qualitative inputs are stale. **The strategist must not silently treat a 2-day-old thesis map as fresh** — it already has the `as_of` stamps from `merge-tails`; this dispatch simply doesn't give it anything newer to replace them with, and it should say so per name where it matters (e.g. a `catalyst_threat` trigger firing on stale news).
7. **Merge and apply exactly as a normal Stage-2 return:** `merge-tails --agents strategist`, then `commit-state --run-dir runs/<ts>` (merge-tails only stages), then `add-proposal` for anything new, then `proposals --run-dir runs/<ts>` to re-run auto-retirement/dedup against the fresh trigger set — a proposal whose trigger has now objectively cleared (§2.9d retirement conditions) gets retired here, not left open on stale grounds.
8. **Dashboard + persist + ledger, same as any dispatch that changed proposals:** rebuild via `smith_dashboard.py`, publish, persist state.json (book/holdings/session/gate), append ONE ledger row (unlike a plain §0.5 refresher, this mode DOES change proposals and therefore does warrant a row — label the summary "priced refresh" so the series distinguishes it from both a plain refresher and a full sweep).
9. **State the mode plainly at the top of the briefing**: "PRICED REFRESH — prices, session, triggers and proposals are live as of `<ts>`; thesis/signals/watchlist last refreshed `<prior full-sweep ts>`." This is the one line that would have prevented the 2026-09-09 confusion: it tells the user exactly which layer is current and which isn't, rather than leaving them to infer it from a header that looked complete.

**What this deliberately does NOT do:** it does not dispatch smith-signals/thesis/watchlist/scout/macro — genuinely new news or a thesis re-read still needs a full quick or deep sweep. If the user's real question is "has anything actually changed," not "are the numbers current," redirect to a full sweep instead.
